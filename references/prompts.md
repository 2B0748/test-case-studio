# 可导出提示词模板（外部工具用）

本文件供 `test-case-studio` 的**导出模式**使用：仅当用户明确说"给我提示词"
"我要拿去别的平台/工具用"时，才把对应阶段的提示词输出给用户。
正常对话中不要主动输出本文件内容，直接按 SKILL.md 的四阶段指令执行。

> 使用说明（告知用户）：下列提示词均为"即贴即用"模板，把方括号 `[...]`
> 占位符替换为实际内容即可。每个提示词可单独发给模型执行，也可连续串联完成四阶段。

---

## Prompt 1 — 需求理解与测试点拆解

```
你是一名资深测试工程师。请基于以下资料完成"测试点拆解"，不要直接写详细用例。

【输入资料】
[粘贴：PRD / 需求文档 / 用户故事 / 接口文档，或简述需求]

【拆解步骤】
1. 提炼功能清单：按模块/子模块拆出所有可独立验证的功能点。
2. 识别业务规则与约束：字段规则、状态流转、权限、边界、依赖、异常分支。
3. 标注风险与优先级：标出核心主链路(P0)、易错点、历史缺陷高发区。
4. 形成测试点清单：每个测试点一行，含"模块 / 测试点 / 类型(功能·接口·性能·安全·兼容) / 优先级 / 风险说明"。

【输出格式】
## 测试点清单
| 模块 | 测试点 | 类型 | 优先级 | 风险说明 |
|------|--------|------|--------|----------|
| ...  | ...    | 功能 | P0     | ...      |

【要求】测试点粒度要"一个测试点对应一类验证意图"，既不过粗也不直接细化到步骤。
```

## Prompt 2 — 测试设计（方法选择 + 用例生成）

```
你是一名测试架构师。基于上一步的"测试点清单"，为每个测试点选择合适的测试设计方法并展开用例。

【测试点清单】
[粘贴阶段1输出的测试点清单]

【方法选择指引】
- 输入有取值范围/格式约束 → 等价类划分 + 边界值分析
- 多条件组合逻辑 → 判定表 / 因果图
- 状态流转明显 → 状态迁移法
- 业务流程/用户旅程 → 场景法(基本流+备选流)
- 历史缺陷/经验 → 错误推测法
- 参数组合爆炸 → 正交试验 / 两两组合(pairwise)

【生成要求】
1. 每个测试点至少覆盖：正向(正常通过) + 反向(异常/边界/非法输入)。
2. 高风险 P0 测试点必须补充边界值与异常用例。
3. 在每条用例标注所用"设计方法"，便于评审追溯。
4. 接口类额外覆盖：状态码、错误码、超时、幂等、契约(字段类型/必填)；
   性能类额外覆盖：并发、思考时间、目标 TPS/RT、资源水位；
   安全类额外覆盖：注入/XSS/越权/认证绕过/敏感数据；
   兼容类额外覆盖：OS/浏览器/机型/分辨率/版本矩阵。

【输出】直接给出下一阶段所需的标准字段用例（字段：用例编号/模块/子模块/用例标题/
用例类型/设计方法/优先级/前置条件/测试步骤/测试数据/预期结果/需求追溯），暂不排版装饰。
```

## Prompt 3 — 用例编写（格式输出）

```
你是一名测试工程师。把下列设计结果整理为标准化测试用例并输出。

【设计结果】
[粘贴阶段2的输出]

【字段规范】（通用字段，必须全部填写）
用例编号 | 模块 | 子模块 | 用例标题 | 用例类型 | 设计方法 | 优先级 |
前置条件 | 测试步骤 | 测试数据 | 预期结果 | 需求追溯

【类型专属补充字段】
- 接口(API)：请求方法/URL、请求头、请求体、预期状态码、响应校验点
- 性能：并发用户数、持续时间、目标 TPS/响应时间、监控指标
- 安全：漏洞类型、攻击向量、预期防护结果
- 兼容：环境矩阵(OS/浏览器/机型/分辨率/版本)、预期表现

【标题写法】"【类型】【预期】动作+对象"，如"【功能】【正常】用户使用正确密码登录成功"。
【步骤写法】每步一个动作，含可操作指令；预期结果可判定、可观测。
【输出】Markdown 表格，多类型混合时按"功能 → 接口 → 性能 → 安全 → 兼容"分表。
单元格内多行内容用 <br> 分隔。
```

## Prompt 4 — 用例评审（自检 + 评审清单）

```
你是一名测试用例评审专家。请评审下面这组用例，给出可执行的修订意见。

【待评审用例】
[粘贴阶段3输出的用例]

【评审维度】（逐条核对）
1. 覆盖度：需求点是否 100% 覆盖？正向/反向/边界/异常/分支是否齐全？P0 是否充分？
2. 正确性：预期结果是否明确、可判定？是否存在"显示正确"这类不可验证描述？
3. 可执行性：步骤是否可复现？前置条件/测试数据是否齐备？环境是否明确？
4. 独立性：用例之间是否无依赖、可单独执行？
5. 颗粒度：是否一个用例验证一个点？步骤粒度是否适中？
6. 可追溯：需求追溯字段是否填全、可回溯到原始需求？
7. 优先级：P0/P1 划分是否合理？
8. 去重：是否存在冗余重复用例？

【输出格式】
## 评审结论：通过 / 有条件通过 / 打回
### 问题清单
| 用例编号 | 维度 | 严重度(高/中/低) | 问题描述 | 修订建议 |
### 覆盖度统计
- 需求覆盖率：X/Y (Z%)
- 缺失/薄弱的测试点：[...]
### 修订后用例
[直接给出修订后的完整用例表]
```
